# LRN-024 — `Intl.DateTimeFormat(locale, { hour: "2-digit" })` seul renvoie une chaîne décorée, pas un nombre pur

`new Intl.DateTimeFormat("fr-FR", { hour: "2-digit", hour12: false }).format(date)` sans `minute` renvoie `"12 h"` en français (pas `"12"`). `Number("12 h")` → `NaN`, silencieusement sérialisé en `null` par `JSON.stringify`. Conséquence réelle : le widget horloge multi-fuseaux (`useZoneClocks`) affichait toujours l'icône lune, même en plein jour, car la comparaison `hour >= 6 && hour < 20` était toujours fausse avec `NaN`.

**Fix** : utiliser `formatToParts()` et lire le part `type === "hour"` pour extraire un nombre fiable, indépendant des espaces/lettres ajoutés par la locale — ou `Intl.DateTimeFormat("en-US", ...)` qui ne décore pas la sortie.

**Comment appliquer** : dès qu'un calcul (pas juste un affichage) dépend d'une valeur extraite d'un `Intl.DateTimeFormat().format()`, ne jamais faire `Number(...)` dessus directement — utiliser `formatToParts()`. Même piège rencontré côté **affichage** dans le widget "Météo horaire" (`weather-md-02.tsx`) : `date.toLocaleTimeString("fr-FR", { hour: "numeric" })` rendait `"7 h"`, et le JSX ajoutait encore un `h` littéral → `"7 hh"` affiché à l'écran. Fix : `date.getHours()` natif (nombre pur, zéro Intl) quand on n'a besoin que de l'heure locale du navigateur. Vérifier aussi ce genre de bug en testant dans le vrai navigateur (`javascript_tool`), pas seulement en lisant le code : le typage TypeScript ne détecte pas un `Number(string)` qui devient silencieusement `NaN`, ni une chaîne décorée qu'on affiche telle quelle.
