# LRN-025 — Un index mémoire lu en début de session peut être périmé au moment d'écrire

En début de session, j'ai fait le grep/lecture obligatoire de `decisions.md`/`learnings.md` (dernier ID vu : BDR-020/LRN-018) puis, plus tard dans la même conversation, écrit de nouvelles entrées `BDR-021`/`LRN-019` sans re-vérifier l'index juste avant. Entre-temps, une session parallèle avait committé (`e814fa9`) de nouvelles entrées qui utilisaient déjà ces mêmes IDs (`BDR-021` "Flux RSS", `LRN-019` "dumpsys gfxinfo") — mon `Write` a **écrasé silencieusement** leur contenu, sans erreur (git status a bien montré `M` au lieu de `A`, seul signal visible, repéré seulement au rituel `/memory-close` suivant en comparant `git show HEAD:<path>` vs le contenu actuel).

**Fix appliqué** : `git checkout -- <fichier>` pour restaurer l'original, puis récréation du contenu sous le prochain ID réellement libre (relu depuis l'index à cet instant précis).

**Comment appliquer** : avant d'écrire un nouveau fichier dans un registre partagé/versionné (mémoire agent, mais aussi tout append-only log/index modifiable par un autre processus), **re-lire l'index juste avant l'écriture**, pas se fier à un état lu en tout début de conversation — surtout en session longue, après compaction, ou si un commit mémoire (`🧠`) a pu atterrir entre-temps. Un signal de détection après-coup : `git status --porcelain` montrant `M` (modifié) au lieu de `A` (nouveau fichier) sur un chemin qu'on pensait créer — c'est la preuve qu'un fichier existait déjà.
